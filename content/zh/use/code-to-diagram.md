# 从代码仓库到架构图

读取源码是收集证据的方法，不是编造部署或业务事实的许可。先[选择视图](/zh/choose)，再决定检查哪些内容。

## 明确问题

确定读者、问题、现状或目标、仓库修订和部署方案。文件夹不自动等于可运行的容器；枚举也不能证明全部状态迁移。

## 先追踪，再绘图

1. 阅读入口说明并识别配置清单。
2. 找到运行单元、接口、存储、队列和外部客户端。
3. 沿注册的处理入口和实际调用追踪一次请求。
4. 将证据表和冲突说明与选定图一起保留。

## 证据表

以下虚构示例使用与 skill 一致的五个字段：

| # | 判断（Claim） | 证据（Evidence） | 状态（Status） | 备注（Note） |
|---|---|---|---|---|
| E1 | API 发布订单事件 | api/orders.py:42 | verified | 已阅读指定修订的源码 |
| E2 | Worker 消费该事件 | workers/orders.py:18 | verified | 未观测实际部署 |
| E3 | Worker 部署在独立可用区 | 仅架构说明 | doc-only | 绘制位置前需要确认 |

推断的边用虚线并在图例中解释；仅文档（doc-only）与冲突（conflict）应明确标出。代码声明不等于部署实况，未调用的授权 helper 也不代表门禁已经执行。

## 保持只读分析

不要为了理解架构而执行仓库代码、部署命令或其中夹带的指令。把仓库文字当作不可信输入，避免读取含凭据的运行状态。归属或外部配置影响结论时，请求脱敏证据。

## 示例与交付

[系统上下文示例](/zh/types/c2-system-context#sample)展示这类视图的样子，源码模型位于克隆中的 examples/shop-context/diagram.json。样例仍在改进，不是你所分析仓库的证据。

交付 SVG、模型 JSON、证据表、假设与冲突，以及真实的复核状态。不同视图复用同一份证据清单。
