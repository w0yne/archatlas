# Container Diagram (容器图)

> The zoom into one system: the applications and data stores that must be running, their technology, and how they talk.

## Meaning {#meaning}
<!-- skill: condense (4–6 lines) -->
It answers: *which separately running applications and data stores make up this system, what technology does each use, and how do they communicate?* It is Level 2 of the C4 model, Simon Brown's notation-independent method (no versioned standard) [1][6], and shows the overall shape of the architecture, how responsibilities are split and the key technology choices [2]. In arc42 terms it is the building-block view, level 1 [3][4]. It leaves out deployment topology (replicas, zones, load balancers belong in G1), the inside of each container (C4), classes, sequences over time and data models [2].
**Definition used here: a container is not a Docker container.** A C4 model container is an *application or a data store* that must be running for the system to work: a server-side web app, a single-page app in the browser, a mobile or desktop app, a batch process, a serverless function, a database or schema, an object-storage bucket, a file share, even a script [8]. It may or may not match a Docker/OCI container. JARs, DLLs, packages, modules and shared libraries are *not* containers; they organise code inside one [8][15].

## When to use and how to choose {#choose}
<!-- skill: condense (bullets, ≤12 lines) -->
- **Audience:** technical readers inside and outside the team; the C4 model recommends it for all software teams [2].
- **Scenarios:** the first technical picture for a new engineer; design or technology-choice review; "what runs and what talks to what" before security, operations or threat-model work (F2); impact analysis of a change or outage.
- **When not to use:** readers cannot read technology names (C2, A7); the question is placement, capacity or environments (G1/G2/G3); the subject is a library or SDK (the C4 model targets software systems) [4]; technology is still undecided (draw C5 first); you are tempted to invent containers to fill a two-box system.
- **vs neighbours:**
  - Choose **C2** for scope and dependencies only, or for non-technical readers; draw it first [10]. Choose **C1** for many systems (the C4 model System Landscape diagram) [13].
  - Choose **C4** when one container is complex and developers need its parts [11]; class-level code diagrams are optional and best generated by an IDE [12].
  - Choose **G1** when the question is *where, how many, which environment*; never pass a container diagram off as one [2][9].
  - Choose **C5** for technology-neutral responsibilities; C3 labels every container with technology.
  - Choose **C6** for interfaces *between* systems with full attributes; C3 stays *inside* one system and its direct neighbours.
  - Choose **E1** for one scenario over time (the C4 model "dynamic" diagram is a numbered-interaction form of it [14]).

## Notation and elements {#notation}
<!-- skill: condense (bullets, ≤15 lines) -->
- **The C4 model mandates no notation**: shapes and colours are free, but a legend is required and the diagram must stand alone [7].
- **Required:** **containers**, each with name, explicit type ("Container"), technology and a one-sentence responsibility [7]; **data stores** with the same four fields (a cylinder is common; explain it in the legend); a visible **system boundary** labelled with the system name; **relationships**; **title** "Container diagram for `<System>`"; **legend** (shapes, colours, borders, lines, arrowheads, acronyms) [2][24].
- **Supporting elements:** the people and external systems from C2 that connect directly to containers; never draw the internals of external systems [2][15].
- **Relationships:** one direction per line; an intent label that agrees with the direction ("Reads from and writes to", "Publishes order events to"); between containers, add the protocol or technology (JSON/HTTPS, SQL, AMQP) [7][8]. Dependency or data-flow direction are both fine if consistent [16]; no double-headed arrows [5].
- **Modelling rules [8][17][18]:** a browser single-page app and its backend are two containers; managed cloud databases and buckets you own are containers, not external systems; one team's microservices are containers (API plus its store, grouped), while services owned by separate teams become separate software systems; model each queue or topic as its own container rather than one "message bus" box (the author's recommendation), or show it only on the arrow label.
- **Box text:** many renderers print name, then `[Container: technology]`, then the description. This is a renderer convention, not verified as a rule in the C4 model text.
- **Tools:** Structurizr DSL [20] and C4-PlantUML [21] support the full element set; Mermaid's C4 model syntax is marked experimental [22].
- **Size:** typically 5–12 boxes; past about a dozen, split by domain or draw one service with its direct neighbours [19].

## Best practices and anti-patterns {#practice}
<!-- skill: condense (top 5 each, no citations) -->
### Best practices
1. Draw C2 first, then C3 with the same system name, people and external systems [2][19].
2. Always show technology and protocol; technology choices are the main value of this level [7].
3. Give each container one responsibility sentence, named by role, matching its name in code and docs [7].
4. Keep it deployment-neutral; replicas, zones and load balancers go to G1 [2].
5. Generate views from one model (diagrams as code) so C2, C3 and C4 stay consistent and do not drift [23][26].

### Anti-patterns
1. Treating "container" as Docker, or drawing shared libraries, modules or JARs as containers [8][15].
2. One "message bus" box hiding who publishes to and consumes from which topic [18].
3. Deployment detail (clusters, subnets, instance counts) on the container diagram [2].
4. Boxes with only a name (no type, technology or responsibility), "Uses" labels, unlabelled or two-way arrows, no legend [15][24].
5. Inventing extra levels ("subsystems") or one giant diagram of a whole distributed estate [15][19][25].

## Drawing recipe {#recipe}
<!-- skill: keep (≤25 lines) -->
1. Confirm the system boundary and the C2 neighbours; if there is no C2, list them first.
2. Inventory running units and stores (e.g. online shop: Web Shop single-page app, Mobile App, Shop API, Order Worker, Order Database, Search Index, Product Image Bucket, an "order placed" topic).
3. Decide with the user: one team's services = containers; separately owned services = separate systems.
4. Write four fields per container: name, type, technology, one-sentence responsibility.
5. Write each relationship as verb phrase + protocol ("Sends payment requests to — JSON/HTTPS"); one direction convention throughout.
6. Layout top-to-bottom or left-to-right: people and client apps first, application containers in the middle, stores and topics last; external systems (Payment Provider, Warehouse System, Customer Support System, Email Service) outside the boundary on the side they are reached from.
7. Text budget: name 2–4 words, technology one line, description up to about 12 words, arrow label up to about 6 words plus protocol.
8. Colour: 3–4 semantic colours (container, store, external system, person) plus a shape cue; explain them in the legend.
9. Add title, legend and date; no status notes or TODOs; more than about 12 boxes → split into several views.

**Self-check**
- [ ] Title, type, scope and legend visible; system boundary explicit.
- [ ] Every box is an application or data store that must run; no libraries, packages, classes, servers or subnets.
- [ ] Every container shows name, type, technology and responsibility.
- [ ] Every arrow has one direction, an intent label matching it, and a protocol between containers.
- [ ] No deployment detail and no internals of external systems.
- [ ] Data stores and queues follow one stated rule.
- [ ] Names match the code and the C2 diagram; acronyms explained.
- [ ] Colour is not the only cue; about a dozen boxes or fewer.

## Evidence in a code repository {#evidence}
<!-- skill: keep (≤10 lines) -->
- Compose files, Helm charts, Kubernetes Deployments/StatefulSets, Procfiles: one *candidate* container per service. One compose service is not always one container (sidecars, init jobs); local-only helpers are not part of the system.
- Dockerfiles and build files (`package.json`, `pom.xml`, `go.mod`, `pyproject.toml`): technology per container.
- Infrastructure-as-code: managed databases, buckets, queues and functions (all containers) [8].
- API specs (OpenAPI, AsyncAPI, protobuf) and connection settings (`DATABASE_URL`, broker and service URLs): who calls whom, and with which protocol.
- Service catalogues and trace data can feed automated views [26].
- Not in code: responsibility wording, which dependencies are external, team ownership (needed for the microservice decision) and the reasons behind choices. Ask people.

## Guided-mode questions {#questions}
<!-- skill: keep (≤8 lines) -->
1. Which system is in scope, and do we already have its context diagram? (draw or confirm C2 first)
2. Who reads it, and what should they decide afterwards? (developers and operations reviewing the design)
3. Is it one team's product, or several teams' services? (one team: services are containers)
4. Queues and topics as their own boxes or only on arrow labels; is the technology final? (own boxes; open choices marked "proposed" in the legend)
5. May I read the repository and deployment files, and do you want an editable source? (yes; diagrams-as-code source plus SVG)
